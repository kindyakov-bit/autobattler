# WORKFLOW.md — как делим работу между OpenCode и Qoder

## Зачем
Qoder тратит кредиты за каждый turn; OpenCode практически безлимитен (лишь лимит
запросов в час). Значит **объём делает OpenCode**, а Qoder включается только там,
где нужна сильная модель: ревью, архитектура, тонкие баги, баланс.
Цель — растянуть кредиты Qoder, не теряя качества.

## Роли
- **OpenCode** (main + `worker`): черновик плана, реализация, тесты, самопроверка, доки.
- **Qoder**: утверждение плана/контракта, milestone-ревью, финальная верификация,
  трудные баги и архитектурные развилки.
- Технические правила репозитория (слои, инварианты, команды): `AGENTS.md`.
- Узкие правки в одном файле / трейсбеки / JSON-баланс: `.opencode/agents/worker.md`.

## Цикл (контрольные точки)
1. **План.** OpenCode набрасывает спеку + критерии приёмки.
   Qoder ревьюит план ОДИН раз (или план утверждает пользователь, если экономим совсем).
2. **Контракт.** Регрессионные тесты пишутся/утверждаются ДО реализации
   (tests-as-contract): они фиксируют «что считается правильным».
3. **Реализация.** OpenCode пилит батчами в рамках часового лимита. Qoder не участвует.
4. **Самопроверка.** OpenCode сам гоняет `python -m pytest tests/ -q`, headless-рендер
   для UI (`AGENTS.md`), обновляет `REVIEW_FIXES.md` / state-доки.
5. **Milestone-ревью.** OpenCode готовит бандл (ниже). Qoder ревьюит ОДИН раз
   и возвращает сводные замечания.
6. **Правки.** OpenCode применяет замечания, перезапускает тесты и рендер.
7. **Финал.** Qoder — один верификационный проход.

## Бандл для milestone-ревью
Готовый контекст, чтобы Qoder не исследовал всю базу (это дорогие turn'ы):
- diff изменений (`git diff` / список файлов);
- обновлённый `REVIEW_FIXES.md` / state-док;
- лог `pytest tests/ -q` (зелёный);
- для UI: скриншоты headless-рендера на 2+ разрешениях;
- список открытых вопросов и рисков.

## На что НЕ тратить кредиты Qoder
Это всё делает OpenCode:
- запуск тестов/линтера, поиск по коду, чтение базы «чтобы понять»;
- бойлерплейт, механический рефакторинг, однотипные правки, форматирование;
- генерация ассетов, JSON-балансировка;
- трейсбеки с очевидной причиной.

## Правила экономии
- **Батчи:** один сводный ревью на milestone вместо десятка мелких «глянь ещё вот это».
- **Готовый контекст:** diff + док + лог, а не «посмотри сам весь проект».
- **Живой док:** OpenCode держит инварианты/конвенции актуальными → каждый заход
  Qoder начинается с дешёвого контекста, а не с раскопок.
- **Тесты-контракт:** повторное ревью Qoder сводится к «тесты зелёные + diff небольшой».
- **Трудное — сразу к Qoder:** тонкий баг, баланс, архитектурная развилка.
  Это высокая отдача на кредит; рутину туда не тащить.

## Контроль дрейфа
Чем реже включается Qoder, тем выше риск, что OpenCode «уплывёт» от замысла между
точками. Лечится тестами-контрактом и обязательными milestone-гейтами.
Видишь дрейф — зови Qoder раньше, не копи до финала.

## Темп OpenCode
Часовой лимит запросов: дели работу на батчи; между батчами — самопроверка и док,
а не долбёжка запросами. Qoder зовём по готовности бандла, а не по каждому чиху.
