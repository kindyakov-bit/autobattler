## 1. Симптомы (скриншот пользователя, ROUND 24)

- **Костяной страж** (`undead_warrior_bone_guard`): при 1 копии на доске + 1 на бенче покупка
  3-й из магазина должна сливать в ★2. Вместо этого скамейка стала **10/9** (выше `BENCH_MAX=9`).
  На скрине виден свежий `страж★2` на бенче при заголовке `BENCH (10/9)`.
- **Костяное лезвие** (`undead_assassin_bone_blade`): карточка в магазине **не реагирует на клик**.
  На бенче ровно 2× `лезвие★1`, бенч переполнен.
- **10-й юнит бенча невидим и не продаётся мышью**: отрисовка `ui/game_ui.py:1555`
  (`player.reserve[:BENCH_MAX]`) и клик-хендлер `ui/game_ui.py:2275`
  (`range(min(len(player.reserve), BENCH_MAX))`) обрезают до 9. Переполнение = **софт-лок**
  (клавиша S ещё продаёт последний юнит, но мышью лишний не увидеть/не перетащить/не продать).

## 2. Корневые причины (все воспроизведены)

1. **`game/core/shop.py:110-117` — проверка полного бенча считает копии НЕ той звезды.**
   `base_name(r) == base` считает ★1+★2+★3 вперемешку, а `_maybe_merge`/`_count_copies`
   (`shop.py:179-183`) сливают только **точные** совпадения имени (★1 с ★1, ★2 с ★2).
   *Репро:* бенч 9/9 = `[лезвие×7, страж★2, страж★2]`, доска `[страж★1]`.
   `buy(страж)` → `base_copies=3` → разрешено → `reserve.append` → **10/9**, merge НЕ сработал
   (точных ★1 = 2, ★2 = 2). Золото списано, копия пула взята.

2. **`game/core/shop.py:116` — off-by-one: `if base_copies < 3` не учитывает покупаемую копию.**
   Сценарий «1 на доске + 1 на бенче + 1 в магазине» = 2 имеющиеся + 1 покупаемая = 3, но проверка
   требует 3 **уже имеющихся** → `ShopError "резерв полон"` → покупка, которая ДОЛЖНА слиться,
   отвергается. *Репро:* бенч 9/9 (1 страж), доска `[страж★1]`, `buy(страж)` → `ShopError`.
   Этим же объясняется «лезвие не нажимается» на скрине: 2× лезвие★1 на бенче → `2 < 3` → отказ.

3. **`ui/game_ui.py:2262-2263` (а также `2060-2061` клавиша W, `2253-2254` предметы) —
   `except Exception: pass` глотает `ShopError` молча.** Любая причина отказа (полный бенч, мало
   золота, пустой пул) невидима → карточка «не нажимается».

4. **`game/core/shop.py:238 и 246` — результат merge ВСЕГДА кладётся в `reserve`.**
   Даже после починки подсчёта (п.1-2) остаётся overflow: если 2 копии на доске и 0 на бенче
   (полный бенч), merge снимает 1 из reserve + 2 с доски и кладёт ★2 в reserve → **10/9**.
   *Репро:* бенч 9/9 (стражей нет), доска `[страж★1×2 с row/col]`, покупка + `_maybe_merge`
   → `reserve=10/9, board=0`. **Это главная причина overflow на скриншоте** (свежий ★2 на бенче).

5. **`game/core/shop.py:168-177` и `game/core/player.py:127-133` — `remove_from_board` кладёт
   в reserve без проверки лимита.** *Репро:* бенч 9/9, доска `[страж]`, `remove_from_board(0)`
   → **10/9**. Тот же инвариант, другой путь.

## 3. Инвариант (единый источник истины)

После **любой** операции `len(player.reserve) <= player.max_bench`
(`BENCH_MAX=9`, `game/core/player.py:6`).
Учёт пула `POOL_COST_BY_STAR` (`shop.py:9`) и refund при merge (★2 → 2 копии, ★3 netto 3)
**не менять**.

## 4. Что сделать (узко, без рефакторинга соседних модулей)

### 4.1 `Shop.buy()` — точный подсчёт + учёт покупаемой копии (`shop.py:110-117`)
Магазин продаёт только ★1-имена (без суффикса). Заменить проверку на:
```python
if len(player.reserve) >= player.max_bench:
    # Покупка разрешена, если покупаемая копия завершает тройку ТОЙ ЖЕ звезды:
    # 2 точные копии (резерв+доска) + 1 покупаемая = 3 -> merge освободит место.
    if self._count_copies(player, name) < 2:
        raise ShopError(f"резерв полон ({player.max_bench}), разместите или продайте юнита")
```
`_count_copies` уже считает точные совпадения в reserve+board — переиспользовать, не дублировать.
Чинит и ложное разрешение (п.1), и ложный отказ (п.2). Бонус: выводит текущее залипшее состояние
со скрина (2× лезвие★1 + переполнение → покупка лезвия разрешится и сольётся, бенч вернётся к 9).

### 4.2 `Shop._maybe_merge()` — размещение результата без переполнения (`shop.py:221-252`)
Правило: результат merge кладём в `reserve`, **только если там есть место**; иначе — на доску
(слот гарантированно освобождён, т.к. копии снимались с доски). Board-юнит **обязан** унаследовать
`row`/`col` первой снятой доски-копии — иначе он не отрендерится и при restore следующего раунда
уедет в reserve (`game_ui.py:1974-1975`) и снова переполнит.
- `_remove_copies` (`shop.py:197-219`) сейчас возвращает только `removed`. Изменить возврат на
  `(removed, board_slot)`, где `board_slot = {"row": u.get("row"), "col": u.get("col")}` первой
  снятой с доски копии (или `None`). Единственный вызывающий — `_maybe_merge`; тесты приватный
  метод не вызывают (проверено).
- В обоих циклах merge (★2 и ★3):
```python
removed, board_slot = self._remove_copies(player, target, 3)
merged = target + "★2"          # для второго цикла: base_name + "★3", star=3
if len(player.reserve) < player.max_bench:
    player.reserve.append(merged)
else:
    unit = {"name": merged, "star": 2}   # star=3 во втором цикле
    if board_slot:
        unit.update(board_slot)
    player.board.append(unit)
```
Предметы снятых доски-юнитов уже возвращаются в `player.items` — сохранить это поведение.
Поведение «результат в reserve» для НЕполного бенча не менять (на нём держатся существующие тесты).

### 4.3 `remove_from_board` — guard лимита (`shop.py:168-177`, `player.py:127-133`)
Перед `player.reserve.append(...)` (проверка ДО `pop`, чтобы юнит не потерялся при отказе):
```python
if len(player.reserve) >= player.max_bench:
    raise ShopError(f"резерв полон ({player.max_bench})")   # в Player — ValueError
```
В UI-обработчике возврата с доски (`game_ui.py:2519`) лимит уже проверяется — там ничего не менять.

### 4.4 UI — видимая причина отказа вместо `except Exception: pass`
В обработчиках покупки (`game_ui.py:2257-2263` клик-юнит, `2250-2254` клик-предмет,
`2052-2061` клавиша W):
- Ловить **`ShopError`** (не голый `Exception`) и показывать короткое сообщение причины ~2 секунды.
  Минимальный механизм: `self.draft_message = (str(e), pygame.time.get_ticks())`, отрисовка в
  `_draw_interactive_draft` рядом с бенчем/магазином, если `ticks - t0 < 2000`. Текст `ShopError`
  уже человекочитаемый на русском — показывать как есть.
- Успешная покупка по-прежнему очищает слот (`shop_items[i] = None`) и играет звук.
- Не глотать неожиданные исключения молча: если ловите шире `ShopError`, логируйте/показывайте,
  а не `pass`.

## 5. Regression-тесты (новый класс в `tests/test_review_regressions.py`)

Каждый тест — один из репро выше. Минимум:
1. `test_full_bench_merge_buy_exact_star` — бенч 9/9 (1 страж★1), доска `[страж★1]`, `buy(страж)`
   → успех, результат `страж★2`, `len(reserve) <= 9`, доска уменьшилась на 1 (или ★2 на доске с row/col).
2. `test_full_bench_mixed_star_no_overflow` — бенч 9/9 (`страж★2×2`), доска `[страж★1]`,
   `buy(страж★1)` → `ShopError` (точных ★1 = 1 < 2), `reserve == 9`, золото/пул не тронуты.
3. `test_merge_result_to_board_when_reserve_full` — бенч 9/9 (стражей нет), доска
   `[страж★1×2 с row/col]`, `buy(страж)` → `reserve <= 9`, ★2 на доске с унаследованными row/col.
4. `test_remove_from_board_full_bench_rejected` — бенч 9/9, доска `[страж]`, `remove_from_board`
   → ошибка, `reserve == 9`, доска не изменилась.
5. `test_bench_invariant_after_buy_chain` — серия покупок/merge/remove, после каждой
   `assert len(reserve) <= BENCH_MAX`.
6. `test_pool_accounting_unchanged` — refund при ★2 = 2, ★3 netto = 3 (как в `tests/test_shop.py`),
   не регрессировал.
7. UI-тест на источник: в `ui/game_ui.py` больше нет `except Exception:` + `pass` на путях покупки;
   есть обработка `ShopError` с сообщением (проверка по тексту файла, как в `TestDraftLayout`).
8. `test_overfull_bench_hidden_unit_softlock` — после любой операции `len(reserve) <= BENCH_MAX`;
   закрепить, что сценарий «2 копии на доске + полный бенч + покупка» не даёт 10/9 (пересечение с
   тестом 3) и что ★2 оказывается на доске с row/col, а не в reserve.
9. `test_blade_buy_recovers_overfull` — состояние со скрина: бенч 10/9 c `лезвие★1×2`,
   `buy(лезвие)` → успех, merge в `лезвие★2`, `len(reserve) <= 9` (восстановление из переполнения).
