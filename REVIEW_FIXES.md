# REVIEW_FIXES — разбор правок после ревью

Этот файл написан для модели, которая продолжит работу в OpenCode. Он объясняет
**что было сломано**, **что теперь**, и **почему** — чтобы не пришлось заново
выводить контекст из кода. Номера строк актуальны на момент правок и со временем
смещаются; надёжнее искать по имени функции/символа (они указаны рядом).

Дата правок: 2026-11-08. Ветка: `main`.

## Как читать

- Каждый баг описан по схеме: **Было → Стало → Почему → Где → Тест**.
- «Где» — файл и символ (имя функции/константы), плюс номер строки на момент правок.
- Все правки покрыты тестами. Новый файл с регрессиями:
  `tests/test_review_regressions.py` (48 тестов: 33 по багам ревью + 6 по layout + 9 по слиянию/бенчу).
- Полная сюита: **275 passed** (`python -m pytest tests/ -q`).
  До правок было 227 — новые 48 закрепляют исправленные инварианты.

## Новые общие инварианты и хелперы

Чтобы правки не разъезжались по файлам, появились единые источники истины:

### `game/core/unit_name.py` (НОВЫЙ файл)
Парсинг имён юнитов вида `base`, `base★2`, `base★3`.
- `base_name(name)` — имя без звезды (`name.split("★")[0]`).
- `star_level(name)` — уровень звезды (1/2/3). **Безопасно**: раньше в ряде мест
  стояло `int(name.split("★")[1][1:])` — срез `[1:]` от цифры давал пустую строку
  и `int("")` падал с `ValueError` на любом ★2/★3.
- `star_multiplier(star)` — `STAR_MULTIPLIERS = {1: 1.0, 2: 1.5, 3: 2.0}`.
  Единый множитель статов вместо разбросанных тернарников
  `1.5 if star == 2 else 2.0 if star == 3 else 1`.

### `game/core/shop.py: accumulate_item_bonuses(unit, stats)` (строка 12)
Единая точка накопления бонусов предмета в `unit["item_bonuses"]`. Кладёт **все**
статы, включая `speed_bonus_pct`. Используется и `Shop.apply_item_to_unit`, и
восстановлением юнитов в UI — чтобы не было двух разных реализаций.

### `game/core/economy.py: pvp_base_damage / pvp_round_damage` (строки 94, 109)
Единая формула PvP-урона для ядра (`round.py`) и UI:
- `pvp_base_damage(round)` = 5 / 10 / 15 / 20 (раунды ≤10 / ≤20 / ≤30 / иначе).
  Это живой баланс UI; раньше `round.py` использовал другие числа 6/12/18/24.
- `pvp_round_damage(round, winner_survivors)` = база + `2 × max(0, winner_survivors)`.
  **Ключевой инвариант**: выжившие берутся у ПОБЕДИТЕЛЯ, не у проигравшего.

### `game/core/player.py: BENCH_MAX = 9` (строка 6)
Единый лимит скамейки для ядра и UI. `game_ui.py` теперь импортирует его
(`from game.core.player import Player, BENCH_MAX`), а не держит свою копию.

## A. Боевые баги ядра и движка

### Баг 1 — двойное применение бонусов предметов
- **Было**: `build_combat_team` применял `item_bonuses` к hp/damage/speed И
  пробрасывал ключ `item_bonuses` в боевой юнит. `BattleSimulator.add_team` видел
  ключ и применял бонусы второй раз. Пример: база 500 + предмет 200 → 900 вместо 700.
- **Стало**: `build_combat_team` применяет бонусы один раз (hp/damage/speed) и
  **не** кладёт ключ `item_bonuses` в результат. `add_team` по-прежнему умеет
  применять `item_bonuses` для «сырых» юнитов, переданных напрямую (без сборки),
  но собранная команда ключа не несёт → двойного учёта нет.
- **Почему**: один источник применения бонусов — сборка команды. Движок оставлен
  обратно-совместимым для прямых вызовов (тесты так делают).
- **Где**: `game/core/team.py:100` (комментарий-инвариант), `engine.py:331`
  (docstring `add_team`), применение в `team.py:58-63`.
- **Тест**: `TestItemBonusSingleSource` (4 теста), `test_engine_does_not_double_apply`.

### Баг 2 — «Проклятие» суккуба (demon_mage_succubus)
- **Было**: активка `buff_next_attack` с `effect.damage_reduction_pct` вешала на
  врага `KIND_DAMAGE_REDUCTION` — это снижение ВХОДЯЩЕГО урона, т.е. щит. Суккуб
  защищал врага вместо того, чтобы ослабить его.
- **Стало**: новый статус `KIND_DAMAGE_DEALT_PCT` (= `"damage_dealt_pct"`) снижает
  ИСХОДЯЩИЙ урон цели. В `_refresh_stats`: `damage *= (1 - pct/100)`.
  `self.damage = max(0.0, damage)` — урон не уходит в минус.
- **Почему**: дебафф «снизить урон цели на 25%» должен уменьшать то, что цель
  НАНОСИТ, а не то, что она ПОЛУЧАЕТ.
- **Где**: `engine.py:37` (константа), `:144` (`_refresh_stats`), `:849`
  (ветка `buff_next_attack`, выбор ближайшего живого врага).
- **Тест**: `TestSuccubusCurseSemantics` — контраст `KIND_DAMAGE_DEALT_PCT`
  (исходящий) vs `KIND_DAMAGE_REDUCTION` (входящий).

### Баг 3 — расовое снижение урона undead
- **Было**: `races.undead.bonuses.damage_reduction_pct` (5%) и расовая синергия
  2/4 (+10/+20%) нигде не применялись — поле терялось по пути в движок.
- **Стало**: `build_combat_team` кладёт `damage_reduction_pct` в боевой юнит
  (`team.py:77,92`); `apply_race_bonuses` считает от базы
  `_base_damage_reduction_pct` (чтобы не накапливалось); `add_team` читает его в
  `u._base_damage_reduction_pct` (`engine.py:383`); `damage_reduction_pct()`
  суммирует базу + щиты с потолком `MAX_DAMAGE_REDUCTION_PCT`.
- **Почему**: снижение урона — такое же расовое свойство, как hp_regen; оно должно
  доходить до `take_damage`.
- **Где**: `synergies.py:237,249-251`, `team.py:77`, `engine.py:171-176,383`.
- **Тест**: `TestUndeadDamageReduction` — одиночный undead = 5%, входящий урон снижен.

### Баг 11 — процентный бафф орков (orc_warrior_chief, «Крик войны»)
- **Было**: `buff_allies` с `effect.damage_bonus_pct` вешал плоский
  `KIND_DAMAGE_BONUS` с `amount=30` → +30 урона, а не +30%.
- **Стало**: новый `KIND_DAMAGE_BONUS_PCT` (= `"damage_bonus_pct"`), в
  `_refresh_stats`: `damage *= (1 + pct/100)`. Ветка `buff_allies` использует его.
- **Где**: `engine.py:36` (константа), `:142` (`_refresh_stats`), `:807` (`buff_allies`).
- **Тест**: `TestOrcPercentageBuff` (100 → 130 при pct=30).

### Прочее в движке
- **O(n²) по логу**: подсчёт киллов каждый тик сканировал ВЕСЬ `self.log`.
  Теперь `log_start = len(self.log)` перед циклом юнитов и срез
  `self.log[log_start:]` (`engine.py:1076,1144`) — только новые события тика.
- **Звёздный парсинг**: `round.py` и UI переведены на `star_level`/`base_name`
  (см. баг 4/13 и раздел C).

## B. Магазин, пул, предметы

### Баг 4 — фантомные копии в пуле и цена ролла
- **Было (пул)**: при слиянии 3×★2 → ★3 код возвращал в пул
  `pool.refund(base + "★2", copies=2)` — ключа `base★2` в пуле НЕ существует
  (пул хранит только базовые имена). Появлялась фантомная запись, засорявшая пул
  и `_roll_candidates`.
- **Стало (пул)**: возврат убран. Каждый ★2 уже вернул 2 копии при своём создании,
  поэтому ★3 netto стоит 3 базовых копии. Проверено: 9 покупок cost-1 (30 копий)
  → один ★3, `available == 27` (30 − 9 + 6), в пуле только ключ `warrior_freshman`.
- **Было (ролл)**: если юнитов выпавшей стоимости `target_cost` не было, фолбэк
  брал любого доступного, но цена карточки оставалась `target_cost` (например,
  юнит за 3 показывался как за 1).
- **Стало (ролл)**: фолбэк ограничен реальными ключами `self.unit_costs`
  (+ фильтр уже собранных ★3), цена карточки = `self.unit_costs[unit_name]`.
  Проверено: 2000 карточек на уровнях 1–10, 0 неверных цен.
- **Где**: `shop.py:214` (`_maybe_merge`, ветка ★3), `:247` (`roll`).
- **Тест**: `TestPoolStar3Accounting`, `TestRollCost`.

### Продажа с учётом звезды
- `sell` возвращает в пул копии по звезде: `POOL_COST_BY_STAR = {1:1, 2:1, 3:3}`
  (`shop.py:9,116`). ★2 netto стоит 1 копию (3 покупки − 2 refund), ★3 — 3.
  Это сохраняет существующие тесты (`test_shop.py`: продажа ★2 → refund 1).

### Баг 12 — предметы на скорость не работали
- **Было**: `apply_item_to_unit` вручную раскладывал статы, а `speed_bonus_pct`
  мутировал прямо в `attack_speed` юнита доски. Но `build_combat_team` читает
  `item_bonuses`, а не `attack_speed` → скорость в бой не попадала.
- **Стало**: `apply_item_to_unit` вызывает `accumulate_item_bonuses` (все статы в
  `item_bonuses`), предмет сохраняется в `unit["items"]` для возврата при продаже.
  Удалён неиспользуемый стаб `remove_item_from_unit` (возвращал `None`).
- **Где**: `shop.py:12` (хелпер), `:322` (`apply_item_to_unit`).
- **Тест**: `test_speed_item_reaches_combat`, `test_accumulate_item_bonuses_stores_all_stats`.

### Баг 5 — `Player.place`
- **Было**: парсинг звезды мог падать на ★2; плюс `reserve.remove(name)` стоял
  ДО проверки полноты доски — на полной доске юнит удалялся из резерва и терялся.
- **Стало**: `star_level(name)`; проверка `board full` ДО удаления из резерва.
- **Где**: `player.py:116`.
- **Тест**: `TestPlayerPlace` (★2 размещается; полная доска сохраняет резерв).

## C. Прогрессия, экономика, UI (`ui/game_ui.py`, `round.py`)

### Баг 6 — PvP-урон от выживших победителя
- **Было**: и в `round.py`, и в UI на победе игрока урон боту считался как
  `base + 2 * surviving_enemies` (выжившие врага = 0 при аннигиляции), а на
  поражении игрока — `base + 2 * surviving_players` (выжившие игрока = 0).
  Бонус за выживших не работал никогда; числа базы в ядре и UI расходились.
- **Стало**: обе стороны используют `pvp_round_damage(round, winner_survivors)`:
  победа игрока → `surviving_players`, поражение → `surviving_enemies`.
  Локальный тернарник базы в UI удалён — формула одна на ядро и UI.
- **Где**: `round.py:191,199`; `game_ui.py:3497,3505`; `economy.py:109`.
- **Тест**: `TestPvpDamage` (формула + интеграция: победа бьёт бота на
  `base+2×выжившие_игрока`, поражение бьёт игрока на `base+2×выжившие_врага`).

### Баг 7 — серии побед/поражений в UI
- **Было**: UI читал `win_streak/loss_streak` для `round_economy`, но никогда не
  вызывал `record_win/record_loss` после PvP → стрики застывали, бонус не работал.
- **Стало**: в PvP-ветке перед экономикой вызывается `self.player.record_win()`
  при победе и `record_loss()` при поражении (крип-раунды стрик не трогают —
  как в ядре).
- **Где**: `game_ui.py:3495` (и `record_loss` рядом).
- **Тест**: `test_streaks_recorded_after_pvp` (проверка исходника).

### Баг 8 — пустая доска сбрасывала состояние
- **Было**: `existing = {...} if stored_player_units else None`. Пустая доска
  `[]` falsy → `existing=None` → драфт начинался «с нуля»: золото=5, уровень/опыт/
  предметы/скамейка/стрики терялись.
- **Стало**: `if stored_player_units is not None else None`. После первого драфта
  состояние переносится, даже если доска пуста.
- **Где**: `game_ui.py:3371`.
- **Тест**: `test_empty_board_does_not_reset_state`.

### Баг 9 — потеря юнита при Enter во время драга
- **Было**: перетаскивание юнита с поля сразу убирало его из `player.board`
  (возврат в `MOUSEBUTTONUP`). Если нажать Enter / «Начать раунд» не отпуская
  мышь, юнит не возвращался и исчезал из `board_format`.
- **Стало**: после выхода из цикла драфта любой незавершённый board-драг
  возвращается на исходную клетку (`drag_board_orig`), состояние драга
  сбрасывается. Бенч-драг юнит из reserve не удаляет — просто сброс состояния.
- **Где**: `game_ui.py:2529` (блок восстановления перед сборкой `board_format`).
- **Тест**: покрыто структурно; логика возврата зеркалит `MOUSEBUTTONUP`.

### Баг 10 — shop.level после buy_xp
- **Было**: `buy_xp()` поднимал `player.level/max_board`, но `shop.level`
  оставался старым → ролл шёл по старым шансам до следующего раунда.
- **Стало**: после успешного `buy_xp()` — `shop.level = self.player.level`,
  затем реролл.
- **Где**: `game_ui.py:2150`.
- **Тест**: `test_shop_level_synced_after_buy_xp`.

### Баг 13 — бой брал только первые 6 юнитов
- **Было**: `build_combat_team(player.board[:6], ...)`. Лимит доски =
  `player.max_board = player.level` (до 10), но в бой шли только 6 → на уровнях
  7+ лишние юниты не воевали.
- **Стало**: `build_combat_team(player.board, ...)` — вся доска (размещение и так
  ограничено `max_board`). Второй сайт `board[:6]` был в мёртвом методе
  `draw_draft_phase` — он удалён целиком (см. раздел D).
- **Где**: `game_ui.py:2544`.
- **Тест**: `test_combat_uses_full_board_not_six`.

### Баг 14 — золото за реролл
- **Было**: `player.gold -= ROLL_COST` ДО `try: _mixed_roll(...)`. При ошибке
  ролла золото списано, витрина не обновилась.
- **Стало**: `try/except/else` — золото списывается только в `else` (успешный ролл).
- **Где**: `game_ui.py`, обработчик `K_r`.

### Звёздный парсинг и множители в UI
- Все `int(name.split("★")[1][1:])` (ломались на ★2) → `star_level(name)`.
- Все тернарники `1.5 if … == 2 else 2.0 if … == 3 else 1` → `star_multiplier(...)`.
- `int(name.split("★")[1]) if "★" in name else 1` → `star_level(name)`.
- Затронуты: восстановление юнитов, размещение с бенча/драга, `make_battle_units`
  (бот-vs-бот превью, `game_ui.py:3833`), состав бота в интерактивном матче.
- **Тест**: `TestStarHelpers`, `test_no_broken_star_parsing`.

### `round.py` / `bots.py`
- `_bot_draft_with_shop`: боту передаётся реальный `synergy_data` (было `{}` →
  синергийная логика MEDIUM-бота не работала); `except Exception` → `except ShopError`

- **Тест**: `test_round.py`, `test_bots.py`, `test_match_flow.py` (все зелёные).

## D. Дубли, мёртвый код, производительность

- **Дубль `TIER_COLORS`** (+ `TIER_COLOR_DEFAULT`, `STAR_CHAR`, `KILL_GOLD_PER_UNIT`)

  менял флаги (init без SRCALPHA) и не переприсваивал `self.screen`. Удалено.
  **Тест**: `test_no_per_frame_set_mode` (set_mode остался только в init).
- **`SysFont` каждый кадр**: эффекты боя создавали шрифт на каждый кадр. Добавлен
  `_cached_font(size, bold)` c `@lru_cache` (`game_ui.py:32`), используется в
  рендере имени способности и `_font_render`.
- **Мёртвый `draw_draft_phase`** (~90 строк, `game_ui.py`) — не вызывался нигде
  (рисует только `_draw_interactive_draft`), содержал латентный баг

## F. Слияние ★ и лимит скамейки (`game/core/shop.py`, `game/core/player.py`, `ui/game_ui.py`)

Скриншот пользователя (ROUND 24): покупка 3-й копии при 1 на доске + 1 наベンче

### Баг 16 — неточный подсчёт копий при покупке на полномベンче
- **Было**: `shop.py:110-117` — `base_copies` считал копии по `base_name` через все звёзды
  (★1+★2+★3 вперемешку), а `_maybe_merge`/`_count_copies` сливали только точные совпадения.
  Проверка требовала 3 **уже имеющихся** копии, не учитывая покупаемую.
  *Репро*:ベンч 9/9 = `[лезвие×7, страж★2, страж★2]`, доска `[страж★1]`.
  `buy(страж)` → `base_copies=3` → разрешено → `reserve.append` → **10/9**, merge не сработал
  (точных ★1 = 2, ★2 = 2). Золото списано, копия пула взята.
  *Репро 2*: 2× лезвие★1 на 벤че → `2 < 3` → `ShopError` → карточка «не нажимается».
- **Стало**: `shop.py:buy()` — при полномベンче покупка разрешена, если

  слияние освободит место). `_count_copies` уже считает точные совпадения — переиспользуется.
- **Почему**: ложное разрешение (overflow) и ложный отказ («не нажимается») исправлены одним

- **Тест**: `test_full_bench_merge_buy_exact_star`, `test_full_bench_mixed_star_no_overflow`.

## G. Новая стратегия боя: все против所有那些х (`game/core/round.py`, `ui/game_ui.py`)

Пользователь пожаловался: у игрока может быть 2 HP, но он не теряет их, потому
что не с кем драться — в старой схеме игрок сражался только с одним ботом за
раунд, остальные боты простаивали. Также не было ротации соперников — не все
играли со всеми поровну.

### Что изменилось
- **Было**: каждый PvP-раунд — один бой игрока с одним ботом (по кругу через
  `self.pvp_round_index`). Остальные боты не участвуют в бою этого раунда.
- **Стало**: все живые участники (игрок + живые боты) делятся на пары
  (1-й со 2-м, 3-й с 4-м, …) и сражаются 1v1 каждый раунд. Порядок пар
  определяется порядком в `living_names`, поэтому при изменении состава
  пары rotiruyutsya естественным образом.
- **Нечётное число живых**: первый участник сражается с копией себя
  (`копия` добавляется в `units_by_name` и `living_names`). Это гарантирует,
  что у всех есть противник, и никто не остаётся без боя.
- **Урон применяется всем проигравшим**: победитель каждой пары наносит урон
  проигравшему по формуле `pvp_round_damage(round, winner_survivors)`.
  Игрок теряет HP при поражении своей пары, боты теряют HP при поражении своих.
- **Экономика и серии**: игрок получает золото и обновляет стрики по результату
  своей пары.

### Почему
Это решает проблему "у игрока нет юнитов, но он не умирает" — теперь игрок
всегда участвует в бое cada раунд (PvP), и если у него нет юнитов, он
проигрывает свою пару и теряет HP. Также все боты развиваются и наносят урон
друг другу, что делает матч динамичнее.

### Где
- `game/core/round.py:Game.run_round_all()` — новый метод, проводит все парные
  бои одного раунда, применяет урон, обновляет серии игрока.
- `game/core/round.py:run_match()` — переработан под новую стратегию, хранит
  `units_by_name` для всех участников между раундами.
- `ui/game_ui.py:run_interactive_match()` — PvP-ветка заменена на парные бои
  всех против所有那些х, копия при нечётном, урон всем проигравшим.

### Тест
- `test_run_match_returns_game` — матч завершается, `game.history` не пуст.
- Все 275 тестов сюиты зелёные.

### Баг — замороженные блоуауты 0%/100% от частых кастов способностей

- **Было**: `cooldown`/`duration` способностей задавались в данных напрямую в **тиках** и декрементировались каждый тик (`engine.py:1320–1321`). `cooldown: 4` = каст каждые 4 тика = 15 раз/сек. Берст абилок на порядок чаще автоатак и полностью доминировал (орк t1 = 3 slinger'а, спамящих `single_target_critical` 60 урона каждые 4 тика — аннигилируют врага до сближения). Поверхностные твики статов/расовых бонусов не двигали винрейты (проверено: ±30% дают идентичный результат). Корень — таймскейл боя, а не баланс чисел.
- **Стато**: введена константа `TICKS_PER_SECOND = 60` (`engine.py:71`). В `add_team` (`engine.py:441–452`) время способности нормализуется из **секунд → тики** один раз на входе (cooldown, duration, mana_per_kill); `reset()` и перекаст читают уже нормализованный `active_ability["cooldown"]` — правок в этих точках не требуется. `wait_ticks`, `damage_per_tick`, `heal_per_tick`, `hp_regen_pct` **не трогаются** (это amounts, не время). Все `cooldown`/`duration` в `data/units.json` переавторины в секунды (коoldown 3/4/5 → 0.6/0.8/1.0; duration щит 2.0 / бафф 2.5 / DoT/HoT/стан/таунт 2.0).

- **Где**: `game/battle/engine.py` (`TICKS_PER_SECOND`, нормализация в `add_team`); `data/units.json` (cooldown/duration всех 78 юнитов в секундах; расовые/юнит-дельты ниже).

## Исправление отображения спрайтов юнитов в бою

### Баг — спрайты юнитов не рисуются (пустые клетки на поле боя)

- **Было**: `_load_sprite` (`ui/sprites.py:182-187`) вызывал `surf.convert_alpha()` / `surf.convert()` без активного дисплея. Оба метода требуют `pygame.display.set_mode()` и падают с `error: No convert format has been set`. Исключение ловилось, поверхность кэшировалась как `None`, и спрайт не рисовался — на поле оставались только ability-круги и текст имён, а сами юниты не видны.
- **Стало**: `_load_sprite` обёрнут во внутренний `try/except`: если оба `convert` не сработали (нет дисплея), поверхность используется без конвертации. Загрузка спрайтов устойчива как в оконном режиме (с `set_mode`), так и в headless без окна.
- **Почему**: `pygame.image.load()` сама по себе работает без дисплея, но `convert_alpha()`/`convert()` требуют установленного формата дисплея. Без fallback-а спрайт терялся полностью.
- **Где**: `ui/sprites.py:_load_sprite` (строки 182-194).
- **Тест**: визуальная проверка `_scratch/render_draft_layout.py 1200 800` — в логе рендера все спрайты загружаются без предупреждений «Спрайт не найден»; `pytest tests/ -q` → 275 passed.
